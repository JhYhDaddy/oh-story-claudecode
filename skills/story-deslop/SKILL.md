# story-deslop: 웹소설의 AI 문체 제거

**문체 결정**: 먼저 [references/style-resolution.md](references/style-resolution.md)를 읽고 이 책의 문체를 로드합니다. 호출자가 전달한 `style_resolution`과 작가 선호를 재사용합니다. 단독 호출이면 현재 요청과 책의 문체를 기준으로 결정합니다. 같은 결정을 후속 실행자에게 전달합니다.

**수정의 중점: 자연스러운 표현, 중심이 있는 서술, 근거 있는 이야기. 진단과 실행 모두 작가가 정한 범위를 따릅니다.**

---

## 실행 범위

- 범위를 지정하지 않은 독립적인 문체 정리는 표현·서술·이야기 세 층위를 모두 검사합니다. 세 층위는 검사 대상이며 단어 빈도로 경중을 나누는 기준이 아닙니다. 각 층위에 문제가 없을 수도 있습니다. 단어·문장, 특정 문단, 특정 문제만 요청하면 그 범위를 존중합니다.
- 일반적인 문체 정리에서는 표현 수정, 기존 연결 복원, 확정 내용의 서술 분량 조정이 가능합니다. 기능이 없는 문단 전체를 삭제할 수 있지만 복선·인과·인물 선택·감정 체험·공개 순서는 보호합니다. 사건·동기·결과를 바꾸거나 새 성립 조건을 넣어야 하면 이야기 층위에서 설계 제안과 승인된 재작성을 구분합니다. 새 미세 동작·욕설·증거·갈등으로 “사람이 쓴 느낌”을 만들면 안 됩니다.
- 문체 결정은 표현에만 영향을 주며 사실과 정보 경계를 바꾸지 않습니다. 정확한 직설, 심리 활동, 관점이 있는 서술, 기능적인 멈춤은 보존할 수 있습니다. Show/Tell, 문장 길이, 삭제 비율을 기계적으로 적용하지 않습니다.
- 검사·표시만 요청하면 진단만 제공하고 본문을 바꾸지 않습니다. “AI 티 제거”, “너무 AI 같다”라고만 하면 수정 요청으로 처리합니다. 표현과 서술은 바로 고치고 이야기의 빈틈은 방안을 제시한 뒤 승인을 받아 고칩니다. 작가에게는 쉬운 말, 원문 위치, 읽기에 미치는 영향으로 보고하며 탐지 분류명·스크립트 필드를 평가 표현으로 쓰지 않습니다.
- 장편 프로젝트(책 디렉터리에 `본문/`와 `추적/`가 있음)에서 사건·관계·인물이 아는 정보·결과를 바꿔야 하면 승인받았더라도 진단과 승인을 `/story-long-write`의 「修改第X章」(X장 수정)에 전달합니다. 그쪽에서 원문을 백업하고 추적 정보를 동기화합니다. 이 절차는 표현·서술·기존 근거에 기반한 연결만 수정합니다.
- 작가의 정체를 추론하거나 탐지 점수를 약속하지 않습니다. 외부 탐지 보고서나 `/story-review` 검토 결과가 주어지면 본문에 대응되는 구체적 문제만 추려 이번 범위로 사용합니다.

### 작가 선호의 경계

호출자가 이미 전달한 작가 선호만 받으며 작가 기억을 조회·기록하지 않습니다. 단독 호출에서는 기억 파일을 로드하지 않습니다. 선호는 자연스러운 경향으로 적용하며 항목별 충족에 집착하거나 일관성·호흡·글자 수를 희생하지 않습니다. 현재 요청, 원문 줄거리의 기능, 이 스킬의 보호 규칙이 우선입니다.

## 문체 정리 절차

### Phase 1: 원문 읽기와 세 층위 검사

본문 경로에서 책 디렉터리와 분량을 판별합니다. 단일 `본문.md`는 보통 단편, `본문/` 아래 장별 파일은 보통 장편이며 작가·프로젝트의 명시적 설명을 우선합니다. 앞의 문체 결정에 따라 책의 요구를 읽고 이번 본문을 통독합니다. 관련 앞부분과 확정 설계만 필요에 따라 찾고 무관한 책 전체를 읽지 않습니다. 자료가 없으면 근거 있는 부분은 계속하고 모르는 부분을 표시합니다. 여러 장이면 장마다 Phase 1–4를 마친 뒤 다음 장으로 넘어가며 집필자에게 맡길 때도 장마다 한 번씩 호출합니다.

기본적으로 아래 방법 세 개를 모두 읽고 검사합니다. 범위가 명확히 제한되면 [references/deslop-gates.md](references/deslop-gates.md)에 따라 필요한 방법을 선택합니다.

| 방법 | 검사 대상 |
|---|---|
| [references/expression.md](references/expression.md) | 먼저 전보체와 짧게 끊긴 문장을 정리하고 어휘·문장, 목소리, 기계적 반복 검사 |
| [references/narrative-focus.md](references/narrative-focus.md) | 장면 기능, 상세함의 정도, 핵심 과정, 세부 묘사의 기능 |
| [references/story-logic.md](references/story-logic.md) | 행동, 인과, 입장, 변화, 결과, 정보를 아는 순서 |

로컬 본문은 먼저 결정적 사전 검사를 실행하며 보고만 하고 수정하지 않습니다. 아래 명령은 모두 이 스킬 루트에서 실행하고 본문 인수는 절대 경로로 전달합니다.

```bash
node scripts/check-ai-patterns.js --check --fail-on=blocking <본문 파일...>
```

스크립트 결과는 위치를 찾는 단서이며 탐지 0건이 세 층위 검사를 대신하지 않습니다. 각 알림의 층위와 판단 기준은 expression.md 마지막 색인을 참조합니다. blocking은 모두 수정하거나 화이트리스트로 보존합니다(Phase 4). advisory는 문맥으로 판단하고 0건을 만들기 위해 기계적으로 수정하지 않습니다. 특정 표현을 찾을 때만 [references/banned-words.md](references/banned-words.md)의 전체 항목을 조회합니다.

파일 첫 6줄 안, 장 제목 아래에 `<!-- 去味:跳过 -->`가 있어도 이번 요청이 문체 정리라면 평소처럼 처리합니다. blocking이 모두 사라지면 이 줄을 삭제합니다. 차단 항목이 남으면 유지하고 해당 장은 여전히 건너뛰기로 처리된다고 보고합니다.

### Phase 2: 문제 위치와 수정 방식 결정

실제 문제마다 원문 위치, 읽기에 미치는 영향, 부족한 근거, 최소 수정안을 기록합니다. 바로 고칠 수 있음, 설계가 필요하지만 미승인, 자료 부족으로 판단 불가의 세 처리를 구분합니다. 문제 수를 억지로 채우거나 표면적 탐지 건수로 나머지 두 층위의 검사 여부를 정하지 않습니다.

이야기의 성립 조건을 먼저 판단하고 장면의 서술 비중을 배치한 뒤 어휘·문장을 처리합니다. 줄거리 빈틈을 당장 고칠 수 없으면 독립적으로 수정 가능한 부분은 계속하고 빈틈은 보고에 남깁니다. 표정이나 요약 문장을 추가해 인과를 고친 것처럼 보이게 하지 않습니다. 승인받은 줄거리 재작성은 실행 범위에 따라 직접 수행하거나 전달하며 같은 승인을 다시 묻지 않습니다.

검사 전용이면 여기서 아래 형식으로 전달하고 본문을 유지합니다. 수정 작업이면 표 내용을 실행 근거로 삼고 Phase 5에서 일괄 전달합니다.

<!-- author-report -->
```md
## 검사 결과
- 표현: {실제 문제, 뚜렷한 문제 없음 또는 이번에는 검사하지 않음}
- 서술: {실제 문제, 뚜렷한 문제 없음 또는 이번에는 검사하지 않음}
- 이야기: {실제 빈틈, 뚜렷한 문제 없음, 자료 부족 범위 또는 이번에는 검사하지 않음}

| 위치와 원문 | 읽을 때의 문제 | 권장 처리 |
|---|---|---|
| {찾을 수 있는 원문} | {구체적인 손실 또는 연결 단절} | {바로 고칠 내용 또는 설계가 필요한 최소 선택지와 영향} |

{자료가 부족하면 무엇을 확인할 수 없는지 명시. 없으면 생략.}
```

### Phase 3: 승인 범위에 따라 수정

> 에이전트 호환성: 현재 호스트만 확인합니다. Claude `.claude/agents/{agent}.md`(`subagent_type`), OpenCode `.opencode/agents/{agent}.md`(`subagent`의 `agent`), Codex `.codex/agents/{agent}.toml`(`agent_type`), Antigravity `.agents/agents/agent-name/agent.md`(`invoke_subagent` + `TypeName`). ZCode는 플러그인에 등록된 동명 역할을 확인하고 실제 스키마에 따라 `Agent`로 전달하며 `.zcode/agents`를 요구하지 않습니다. 역할·도구를 사용할 수 없거나 알 수 없는 에이전트가 반환될 때만 solo/direct로 전환합니다. 작가에게 “이번에는 제가 직접 수정하겠습니다”라고 쉽게 알리고 `Fallback: project custom agents unavailable -> solo` 원문은 보고 마지막 “技术备注：” 줄에만 넣습니다.
>
> Spawn 버전 알림(spawn을 차단하지 않음): 먼저 프로젝트 루트 `.story-deployed`의 `agents_version`을 읽습니다. 이 버전의 `agents_version: 38`과 다르면(표식 없음, 필드 없음/정수 아님, 38보다 작거나 큼) **현재 호스트의 역할 출처를 평소처럼 확인하고 spawn합니다.** (계약 문구: `照常按当前宿主角色来源检查并 spawn`) “집필 보조 에이전트가 이전 버전입니다. /story-setup을 실행하고(ZCode는 플러그인을 먼저 업데이트) 새 세션을 열어 주세요”라고 알립니다. `Notice: agents bundle 版本不匹配（项目 {N}，本版 38）` 원문은 `技术备注`(기술 참고) 줄에 넣습니다. `大于 38 时额外提示先更新 oh-story-claudecode` — 38보다 크면 oh-story-claudecode를 먼저 업데이트하도록 덧붙이고 이전 로컬 setup으로 다운그레이드해 덮어쓰지 않습니다. `只有当前宿主角色缺失或不暴露调用能力时才降级 solo/direct` — 현재 호스트의 역할이 없거나 호출 기능이 노출되지 않을 때만 solo/direct로 전환하며 `Fallback: ... -> solo`도 `技术备注`(기술 참고) 줄에만 넣습니다.

파일을 바꾸기 전에 원문을 책 내부 `.story/work/去味原稿/{YYYYMMDD}_{原文件名}`에 복사합니다. Phase 4에서 대조해 다시 읽고, 작가가 취소를 원하면 이 사본으로 복원합니다.

1. 이미 narrative-writer 내부이면 이번 범위를 직접 실행하고 중첩 spawn하지 않습니다.
2. 주 세션이 현재 런타임의 narrative-writer를 찾아 위 호환성 설명에 따라 호출합니다. 이때만 [references/agent-calls.md](references/agent-calls.md)를 읽고 실제 진단, 원문 근거, 문체, 승인 범위를 전달합니다.
3. 파일이 없거나 런타임이 custom agent를 노출하지 않거나 spawn에 실패하면 주 세션이 직접 수정합니다.

실제 실행자는 세 방법에 따라 수정합니다. 서술 조정은 지나치게 자세한 부분과 생략된 부분을 함께 처리합니다. 기능 없는 과정은 줄이고 기존 대립과 판단은 장면으로 보여 줍니다. 성립 근거가 없으면 이야기 층위로 처리하며 조건을 지어내지 않습니다. 이번 요청의 시점 전환도 각 감각·인식의 출처를 확인하며 정보를 유지하려고 새로운 관찰 경험을 추가하지 않습니다.

### Phase 4: 다시 읽기와 파일 마무리

수정 전 원문, 확정 설계, 승인과 대조해 장면 전체를 다시 읽습니다. 사실·인물 선택·인과·감정 연결·공간 방향·긴장감이 보존되었는지, 상세 서술의 중심이 회복되었는지, 새 상투적 형식이나 줄거리 근거를 넣지 않았는지 확인합니다. 세 층위를 각각 재검사합니다. 정보는 모두 있지만 여전히 항목별로 보고하거나 대사가 개요처럼 보이면 표현 검사는 끝난 것이 아닙니다. 스크립트가 이 읽기를 대신할 수 없습니다.

수정 파일을 저장한 뒤 먼저 다시 검사합니다.

```bash
node scripts/check-ai-patterns.js --check --fail-on=blocking <본문 파일...>
node scripts/check-degeneration.js --check --fail-on=blocking <본문 파일...>
```

- 두 스크립트는 보고만 합니다. 종료 1은 blocking 존재, 종료 2는 명령·파일 오류입니다.
- 문장 형식 blocking: 서사 기능을 유지하면서 자연스럽게 고칩니다. 작가가 명시적으로 선택한 원문은 문체 결정 파일에 따라 화이트리스트에 등록합니다. 둘 다 못 하면 남은 차단 항목으로 나열합니다. 대시는 기능에 따라 고치며 구두점 스크립트의 기계적 치환에 맡기지 않습니다. advisory는 문체와 문맥으로 판단하며 기능적인 표현은 보존하고 설명할 수 있습니다.
- 퇴화 blocking(문자 그대로 반복, 제자리 맴돌기, 잘림, 자리표시자·기술 용어 유출): 손상된 부분을 다시 생성하고 기존 사실을 재확인합니다. advisory는 참고 알림으로만 사용합니다.

의미 수정을 마치고 재검사에 blocking이 없으면 구두점을 정리합니다. 파일 전체의 문체 정리는 기본적으로 수행합니다. 특정 문단·문제만 수정할 때는 실행하지 않고 범위 안에서 수동 정리하며 범위 밖 문제는 알림만 제공합니다.

```bash
node scripts/normalize-punctuation.js <본문 파일...>
```

구두점 스크립트는 화이트리스트 밖의 줄임표·대시·이중 하이픈을 쉼표·마침표·콜론으로 바꾸거나 삭제하며 독립 구분선을 삭제합니다. 물음표·느낌표는 건드리지 않고 따옴표도 기본적으로 바꾸지 않습니다. 작가나 프로젝트가 명시적으로 요구할 때만 `--quote-mode ascii` 또는 `--quote-mode yan`을 추가합니다. 화이트리스트는 문체 결정 파일에 따라 등록하며 스크립트가 경고했다고 임의 허용하지 않습니다.

수정과 재검사를 한 번 완료한 뒤 새로 발견한 구체적 문제에 대해서만 추가 수정합니다. 전체 검사는 최대 세 번입니다. 새 문제가 없으면 멈추고 상한에 도달해도 해결되지 않은 항목은 보고합니다. 스크립트를 사용할 수 없으면 사실대로 밝히고 가능한 의미 검사를 계속하며 통과했다고 주장하지 않습니다.

### Phase 5: 실제 결과 전달

세 층위에서 실제 처리한 내용을 각각 보고하며 여러 장이면 장마다 한 묶음으로 씁니다. 설계 빈틈이 남아 있으면 본문의 모든 문제가 제거되었다고 할 수 없습니다. 수량과 글자 수는 실제 확인한 값만 보고합니다. 삭제 비율이나 “AI 문체 등급 하락”으로 품질 판단을 대신하지 않습니다. 사용자가 별도 보고서 저장을 요청할 때만 보고서 파일을 만듭니다.

```md

- 서술: {줄인 곳, 확대한 곳과 이유. 범위 밖이면 이번에는 검사하지 않음}
- 이야기: {복원한 연결/승인된 설계 수정, 설계 또는 확인이 더 필요한 부분. 범위 밖이면 이번에는 검사하지 않음}

### 대표적인 변경
{소수의 수정 전후 예시와 독자 경험의 변화. 실제로 하지 않은 수정은 나열하지 않음.}

### 남은 처리
{원문 위치, 부족한 내용, 최소 설계 선택지, 영향을 받는 뒷부분. 이미 승인된 수정은 먼저 실행하며 여기서 다시 승인을 요청하지 않음. 없으면 생략.}

{파일 모드: 수정 파일 경로와 200자 이하 대표 구절만 제공하고 전체 본문은 반환하지 않음. 파일 경로 없이 대화에 붙인 짧은 발췌문: 수정본 전체 제공.}
{원문 백업이 있다면: 수정 전 원문은 {백업 경로}에 보관했습니다. 되돌리려면 말씀해 주세요.}
```

## 다른 절차와 연결

표현·서술 수정은 이 절차에서 완료합니다. 장편 줄거리 수준의 변경은 실행 범위에 따라 `/story-long-write`로 넘깁니다. 줄거리 설계가 더 필요하면 구체적인 빈틈과 알려진 제약을 `/story-long-write` 또는 `/story-short-write`로 전달합니다. 작가의 창작 문제를 다른 작품 분석으로 돌리지 않습니다. 전체 원고 검토에는 `/story-review`를 사용할 수 있지만 이러한 연결이 이번에 승인받은 수정을 대신하지 않습니다.
