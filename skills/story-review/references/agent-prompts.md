# story-review: full/lean 모드의 하위 에이전트 호출과 종합

실제 모드가 여전히 full/lean일 때만 읽는다.

현재 런타임의 Agent 도구로 병렬 호출한다. Codex 네이티브 하위 에이전트는 `agent_type`, Claude Code는 `subagent_type`, OpenCode는 `subagent` 도구의 `agent`, Antigravity는 `invoke_subagent`+동명 `TypeName`, ZCode는 `Agent`로 등록 역할을 호출한다. 실제 필드는 현재 CLI가 노출한 도구를 따른다. 각 Agent는 부모 대화 맥락을 물려받지 않으므로 prompt에 프로젝트 경로·검토 범위·파일 경로·필요한 발췌·통일된 Findings Schema를 빠짐없이 넣는다. 구조·인물·문장 관점에는 검토 기준 묶음 요약과 Rubric Source도 인라인으로 넣어 바로 검토할 수 있게 한다. prompt에 이 스킬의 자료 경로를 적지 않는다. reviewer는 자기 템플릿의 읽기 표에 따라 방법 자료를 불러온다. consistency-checker는 자체 점검 항목으로 사실을 확인하므로 내용 채점 기준 묶음을 넣지 않는다. 모든 reviewer는 읽기 전용이며 파일을 수정하지 않고 결과만 출력한다.

**추적 수정 번호**: `추적/_tracking-state.json`이 있는 장편 프로젝트에서 consistency-checker를 호출하기 전에 이 스킬의 `scripts/tracking_commit.py check --project {项目根}`를 실행한다. 출력의 `last_committed_chapter`·`state_revision`을 prompt에 넣는다. check 오류 시 이 칸에 ‘check 실패, 파생 뷰를 신뢰할 수 없음: {오류 첫 줄}’을 쓰고 보고서 `没法判断的地方`에 추적 기록과 본문이 맞지 않아 이번 확인에 쓰지 않았다고 쉬운 말로 적는다. 단편에는 넣지 않는다.

**story-explorer 사전 조회(선택)**: `Effective Mode`가 full/lean이고 현재 spawn이 허용되며 런타임 Agent 도구를 사용할 수 있을 때만 Phase 0의 현재 호스트 소스에서 story-explorer를 확인한 후 spawn한다. ZCode는 플러그인 등록 역할을 확인한다. Antigravity는 `.agents/agents/story-explorer/agent.md`를 확인하고 `invoke_subagent`+`TypeName: "story-explorer"`를 쓴다. solo 또는 하위 에이전트 재귀 보호 상황에서는 spawn하지 않고 직접 읽기/검색만 한다. prompt 예시(필드명은 계약 원형 유지):

```text
项目目录：{dir}
查询类型：setting_appearances
查询参数：{검토에 관련된 설정 키워드}
```

**Agent 1: story-architect**
- full/lean 모두 호출한다.
- 관점: 주제 정렬·개요 구조·훅/반전 품질·범위 통제·플랫폼 기대.
- 지시문(필드명과 출력 스키마는 계약 원형 유지):
  ```
  당신은 story-architect다. 이야기 구조 관점에서 아래 내용을 검토한다.
  임무는 올바름을 확인하는 것이 아니라 문제를 찾는 것이다. 가장 엄격한 기준으로 본다.
  项目路径：{프로젝트 루트}
  审查范围：{파일 경로/장/필요한 발췌}
  文风路径：{작품 문체 전문 경로, 없으면 없음}
  style_resolution：{이번에 적용되는 요구와 출처, 대체된 기본 조항, 사실 경계; 문체 판단에 공통 적용}
  审查基准包摘要：{Phase 1에서 만든 rubric / fallback 요약, 반드시 인라인 포함}
  Rubric Source: file | embedded fallback
  相关文件路径：{설정/개요/상세 개요 경로}
  继承的开放项（分批审查必填，无则写「无」）：{추적/복선.md에서 추출한 회수 예정 장 ≤ 이번 묶음 마지막 장인 심었으나 미회수한 훅과 이전 묶음의 미해결 findings 요약}
  检查项：
  1. 이번 장이 이야기의 주제를 진행하는가?
  2. 개요 구조가 완전한가(훅/쾌감/궁금증)?
  3. 감정 리듬이 적절한가?
  4. 훅과 반전 설계의 품질은 어떠한가?
  5. 범위 통제: 인물/설정이 비대해지지 않았는가?
  6. 줄거리 순환이 있고 반복 가능한가? 기준 묶음 요약의 줄거리 순환 원칙을 따른다.
  7. 절정에 축적·격차·보상이 있는가? 요약의 절정 구성 원칙을 따른다. 가짜 승리→붕괴는 강한 반전의 한 방식이며 필수는 아니다.
  8. 복선 밀도·연재 기대·구조 정보량이 적절한가? 복선 밀도는 이미 이해 혼란을 일으킨 경우가 아니면 보통 S4 구조 위험으로만 본다.
  9. 공통 rubric과 추가 플랫폼 표를 항목별로 대조해 PASS/FAIL을 표시한다.
  10. 이어받은 미해결 항목 중 이번 묶음에서 실현해야 할 훅/복선이 빠졌는가?
  11. 도입 획일화(작품 도입/앞 3장만): 이동 직후 파혼·시스템 연결·종말 첫날·시작부터 되갚기 등 장르 기본 공식인가? 동종 작품 어디에나 그대로 옮길 수 있는가? 훅이 있거나 날씨로 시작하지 않는다고 신선한 것은 아니다. 요약의 도입 신선함 기준에 따라 통째로 옮길 수 있으면 획일화로 본다. 장르 틀과 겹치면 최소 S2, 공식적이지만 구체적인 인물/처지에 작은 차이가 있으면 S3다.
  12. 결말 요약: 장말 요약·의미 부여·재진술이 기존 정보를 반복하며 마무리를 약하게 하는가? 먼저 작품의 서술 방식과 원문의 기능을 확인한다. 탐지기에 잡혔다고 자동 오류 판정하지 않는다. 확인 후 실제 영향으로 등급을 정하고 다른 reviewer의 같은 위치 findings와 중복 제거한다.

  输出格式：
  VERDICT: APPROVE / CONCERNS / REJECT
  FINDINGS: 통일된 Findings Schema를 반드시 사용하며 severity는 S1/S2/S3/S4다.
  INHERITED_ITEMS: 이어받은 미해결 항목마다 확인함 / 확인하지 못함을 적는다. 이번 묶음에서 실현해야 했으나 빠진 것은 finding으로 낸다.
  RECOMMENDATIONS: [수정 제안]
  ```

**Agent 3: narrative-writer**
- full에서 호출한다.
- 관점: 세 층 AI 느낌 진단(표현·서술의 초점·이야기 인과와 변화), 감정 강도(충분히 통쾌한지/지나치게 소극적인지), 형식 준수·리듬 균형·문장의 자연스러움.
- 지시문:
  ```
  당신은 narrative-writer다. 문장 품질 관점에서 아래 내용을 검토한다.

  项目路径：{프로젝트 루트}
  审查范围：{파일 경로/장/필요한 발췌}
  文风路径：{작품 문체 전문 경로, 없으면 없음}
  style_resolution：{이번에 적용되는 요구와 출처, 대체된 기본 조항, 사실 경계; 문체 판단에 공통 적용}
  审查基准包摘要：{Phase 1에서 만든 rubric / fallback 요약, 반드시 인라인 포함}
  Rubric Source: file | embedded fallback
  去味判据：자기 템플릿의 읽기 표에 따라 expression·narrative-focus·story-logic·banned-words·deslop-gates를 전부 읽고 세 층을 모두 검토한다. 방법의 재작성 동작은 제안으로만 쓰고 실제 수정하지 않는다.
  检查项：
  1. 상투어·진부한 말·‘像/好像/仿佛/如同’식 비유의 무더기 같은 문구 신호가 읽기 손실을 낳는가? 단어가 잡힌 것만으로 오류는 아니다.

  9. 표현·서술의 초점·이야기 층의 문제와 증거를 각각 보고한다. 표면 문제의 경중으로 나머지 두 층의 검사 여부를 정하지 않는다.

  输出格式：

  FINDINGS: 통일된 Findings Schema를 사용하며 severity는 S1/S2/S3/S4다. 구체적인 층과 문제는 issue에 쓰고 category는 prose를 사용한다.
  RECOMMENDATIONS: [수정 제안]
  ```

**Agent 4: consistency-checker**
- full/lean 모두 호출한다.
- 관점: grep-first+추론형 일관성 탐지, S1-S4 보고.
- 지시문:
  ```
  당신은 consistency-checker다. grep-first+추론형 일관성 검토로 사실 모순을 찾는다.
  임무는 사실 모순·상태 단절·추론해야 드러나는 설정 논리 충돌을 찾는 것이다. 창작 평가·문학 품질 평가·창작 수정 제안은 하지 않는다.
  项目路径：{프로젝트 루트}
  审查范围：{파일 경로/장/필요한 발췌}
  已知角色：{설정에서 추출한 인물 목록}
  last_committed_chapter：{check 출력; 단편은 「无追踪」}
  state_revision：{check 출력; 실패 시 check 실패, 파생 뷰를 신뢰할 수 없음: {오류 첫 줄}}
  继承的开放项（分批审查必填，无则写「无」）：{추적/복선.md에서 추출한 회수 예정 장 ≤ 이번 묶음 마지막 장인 심었으나 미회수한 복선과 이전 묶음의 미해결 findings 요약}
  检查项：
  1. 인물 속성이 앞뒤로 일치하는가?
  2. 세계 규칙을 위반했는가?
  3. 복선 상태가 일치하는가(已埋/计划回收/已回收/断线: 심음/회수 예정/회수 완료/단절)?
  4. 시간선이 모순 없는가?
  5. 용어·신분·장소·능력 경계가 일치하는가?
  6. 이어받은 미해결 항목 중 이번 묶음에서 회수해야 할 복선이 여전히 떠 있는가?

  输出格式：
  VERDICT: APPROVE / CONCERNS / REJECT
  FINDINGS: 통일된 Findings Schema를 반드시 사용하며 severity는 S1/S2/S3/S4다. category는 consistency / factual / format / causal / rule_boundary만 허용한다.
  INHERITED_ITEMS: 미해결 항목마다 확인함 / 확인하지 못함을 적는다. 이번에 새로 발견했고 복선.md에 없는 열린 훅은 따로 적어 주 세션이 추적 수정 트랜잭션으로 처리하게 한다.
  FACTUAL_RECONCILIATION: [통일할 사실 출처나 사람의 판정이 필요한 항목만 쓰고 문학 창작 제안은 쓰지 않는다]
  REASONING_CHAINS: [추론형 finding의 전제/규칙 -> 계기 사건 -> 모순점 -> 판정이 필요한 질문만 쓴다]
  ```

## 종합 판정

1. 실제 실행한 reviewer의 VERDICT와 FINDINGS를 모은다.
2. 병합·중복 제거: `severity` 순(S1 > S2 > S3 > S4), 같은 등급은 영향 범위 순으로 정렬한다.
3. **선택적 사실 확인**: 역사 연대·지리 방향·직업 세부 등 검증할 외부 사실이 있을 때도 `Effective Mode`가 full/lean이고 현재 하위 Agent가 아니며 런타임 Agent 도구를 쓸 수 있고 Phase 0의 현재 호스트 소스에서 story-researcher를 확인한 경우에만 추가 spawn한다. ZCode는 플러그인 등록 역할을 확인한다. Antigravity는 `.agents/agents/story-researcher/agent.md`를 확인해 `invoke_subagent`+`TypeName: "story-researcher"`를 쓴다. solo·missing/malformed/spawn failed에 따른 강등·하위 에이전트 재귀 보호에서는 spawn하지 않고 보고서에 ‘사람의 사실 확인 필요’만 표시한다.
4. **의견 차이 표시**: reviewer 의견이 충돌하면 차이를 명확히 보여 사용자가 결정하게 한다. 자동으로 절충하지 않는다.
5. SKILL.md의 작가 대상 보고 규칙에 따라 종합 보고한다. 시작에 검토 방식과 범위를 알리고 증거 부족은 작가가 보충할 자료로 표현한다. 실행 경로는 기술 비고 행에만 넣는다.

## 보고서 템플릿

실제 모드가 full 또는 lean일 때만 쓴다. Phase 0이나 런타임 실패로 solo로 강등되면 solo 템플릿으로 바꾼다. lean에서 제외한 관점은 `这次怎么审的`에 적는다. full/lean 필수 reviewer가 없거나 spawn에 실패하면 solo로 강등하며 이 템플릿에서 ‘미검토’라고 적고 계속 종합하지 않는다.
