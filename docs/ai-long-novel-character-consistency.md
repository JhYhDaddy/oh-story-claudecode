# AI 장편 소설의 인물 설정을 유지하는 Oh Story의 방법

이미 일어난 이야기의 상태를 파일에 보관하고 매 장 관련 정보만 읽습니다. Oh Story(`zenstory-ai/oh-story-claudecode`, MIT 오픈소스, Claude Code·Codex·OpenCode 등 코딩 에이전트용 집필 스킬 14개)는 장편을 `설정/`, `개요/`, `본문/`, `추적/` 네 종류의 파일로 나눕니다. 매 장 모르면 잘못 쓰게 될 상태만 읽고 집필 후 스크립트로 변화를 추적 파일에 반영합니다. 대화는 창작을 담당하고 기억은 파일이 담당합니다.

현재 스킬은 구조화된 추적으로 인물 설정의 변화, 복선 단절, 인물이 정보를 너무 일찍 아는 문제를 줄입니다.

[영문판의 한국어 번역](keep-ai-novel-consistent-over-100-chapters.md)

## 일관성이 무너지는 이유

연속성 오류는 장을 쓸 때 제공한 정보가 적절하지 않아 생기는 경우가 많습니다. 최근 몇 장의 본문만 읽으면 3장에서 심은 복선을 잊고, 책 전체 요약을 읽으면 아직 일어나지 않은 계획을 이미 일어난 사실로 취급할 수 있습니다. 텍스트를 많이 넣는 것만으로 사실·계획·인물의 지식을 구분하는 작업을 대신할 수 없습니다.

집필 전에 이번 장에 필요한 사실을 고르고 아직 일어나지 않은 계획을 명시해야 합니다.

## 네 계층의 프로젝트 파일

Oh Story 장편 프로젝트의 구조는 다음과 같습니다. README의 프로젝트 구조에서 발췌했습니다.

```text
{书名}/
├── 설정/          # 세계관, 인물별 파일, 세력, 관계.md
├── 개요/          # 개요.md, 권개요_제1권.md, 상세개요_제001장.md 등
├── 본문/          # 제001장_장제목.md 등
└── 추적/          # 파일 우선 연속성 상태
    ├── _tracking-state.json   # 유일한 구조화된 기준 상태
    ├── 문맥.md              # 파생된 이어 쓰기 상태 카드. 고정 7개 절, 최대 12 KB
    ├── 장별기록/              # 장마다 후속에 영향을 주는 변화만 기록. 최대 3072바이트
    ├── 인물상태/              # 핵심 인물별 현재 스냅샷
    ├── 복선.md                # 복선의 현재 뷰
    └── 시간선/                # 작가용진실.md + 독자가아는사실.md
```

핵심 설계 원칙은 세 가지입니다.

1. **기준 데이터는 하나이고 나머지는 파생합니다.** `_tracking-state.json`만 쓰기 가능한 기준 데이터입니다. `문맥.md`, 인물 스냅샷, `복선.md`, 두 시간선은 여기서 결정적으로 생성합니다. 모든 추적 쓰기는 `scripts/tracking_commit.py`를 거치며 파생 파일을 직접 수정해서는 안 됩니다. `tracking_commit.py check`는 상태에서 다시 렌더링해 파일별로 비교하고 불일치를 찾습니다. 트랜잭션의 예상 개정 번호는 오래된 상태에 기반한 쓰기를 별도로 막습니다.
2. **작가의 진실과 독자가 아는 사실을 구분합니다.** `시간선/작가용진실.md`에는 이야기에서 실제로 일어난 일을, `시간선/독자가아는사실.md`에는 독자가 현재 장까지 본 내용을 기록합니다. 모델이 40장을 쓸 때 범인이 누구인지와 주인공은 아직 모른다는 사실을 함께 확인하므로 인물이 정답을 너무 일찍 말하지 않도록 합니다.
3. **장별 기록은 크기가 제한된 변화분입니다.** `장별기록/제NNN장.md`의 목표는 1536바이트 이하, 절대 상한은 3072바이트이며 이후 연속성에 영향을 주는 변화만 기록합니다. 과거 기록은 계속 쌓이지만 현재 상태 카드는 12 KiB로 제한합니다. 오래된 정보는 필요할 때 조회하며 전체 이력을 본문 프롬프트에 넣지 않습니다.

## 한 장을 쓸 때의 실제 흐름

`story-long-write`의 단일 장 흐름(SKILL.md의 Phase 4)입니다.

1. **필수 자료를 먼저 읽고 씁니다.** 이번 장 상세 개요, 개요 추출 도구가 고른 권 계약과 현재 플롯 단위, 현재 추적 상태를 읽습니다. 집필 전 글자 수 범위, 반드시 일어날 일, 일어나면 안 되는 일, 시간 기준점, 멈출 지점, 장 끝의 새로운 미해결 과제를 기록합니다. 이러한 프로젝트 사실이 모든 집필 기법 자료보다 우선합니다.
2. **모르면 잘못 쓸 정보만 로드합니다.** 등장 인물마다 `설정/인물/{名}.md`의 안정적인 인물 설정과 `추적/인물상태/{名}.md`의 현재 위치·목표·관계·지식·미해결 단서를 읽습니다. “쉬탕에게 오빠가 있다”는 설정이고 “쉬탕은 편지를 보낸 사람이 오빠인 줄 모른다”는 상태입니다. 이를 구분해 읽어야 모델이 설정을 인물이 아는 사실로 바꾸지 않습니다.
3. **본문을 작성합니다.**
4. **검사하고 수정합니다.** 장별 검사는 합의된 플롯 항목, 분량, 문장 패턴, 퇴화를 확인합니다. 일관성 검사는 필요할 때 실행하며 단일 장 집필에서는 커밋 전에 확인합니다. `/story-review`를 별도로 요청하면 다각도 검토를 수행하고 에이전트가 없으면 주 세션에서 처리합니다.
5. **변화를 추적 정보에 반영합니다.** 검사 후 `storyctl.py chapter commit`으로 추적 트랜잭션을 호출하여 누가 무엇을 알게 됐는지, 어떤 복선이 회수됐는지, 시간이 얼마나 지났는지를 기록합니다. 커밋 성공과 파생 뷰 갱신을 확인한 뒤 다음 장으로 넘어갑니다.

하루 3장을 연속으로 쓸 수 있는 이유는 매 장 최신 상태 카드를 받기 때문입니다. 계속 길어지는 대화 기록을 그대로 받는 방식이 아닙니다.

## 이미 수십 장을 썼는데 추적 파일이 없다면

먼저 `/story-setup`으로 배포한 뒤 `/story-import`(`/导入小说`)로 기존 본문을 위 디렉터리 구조로 역분석하고 최초 설정·인물 상태·복선을 생성합니다. 역추론 결과는 작가가 검토해야 합니다. 모델이 일부 내용에서 추측한 설정은 “확인 필요”로 따로 표시하고 사실로 바로 기록하지 않습니다. 이후 `/story-long-write 写第N章`으로 이어 쓰면 가져온 범위 다음 장 N의 상세 개요부터 보완합니다.

## 한계

- 추적은 잊어버림과 너무 일찍 앎이라는 두 오류를 줄입니다. 작가 대신 플롯을 결정하거나 오류가 전혀 없음을 보장하지는 않습니다.
- 작가는 실제로 설정과 상세 개요를 작성해야 합니다. 상세 개요가 없으면 확인을 위해 멈추며, v0.7.7부터는 목표 글자 수가 없는 경우에도 기본 3000자로 대체해 쓰지 않고 중단합니다.
- 이 기능은 기존 코딩 에이전트(Claude Code, Codex CLI, OpenCode, Antigravity, OpenClaw, ZCode, Reasonix) 안에서 실행됩니다. 호스팅 모델을 쓰면 집필을 위한 추가 로컬 GPU나 모델 배포가 필요하지 않습니다.
