# Agent Note: 작가 메모리 프로토콜을 사용 시점별로 나눠 선호 하나를 기록할 때는 일반 부분만 읽음

Status: implemented
Date: 2026-09-26
Related: [35K 로드 상한](2026-09-26-per-call-load-ceiling-35k.md), [작가 메모리의 두 단계 저장소](2026-09-18-author-memory-two-level-store.md)

후속 소유권 조정은 [작가 메모리를 장편·단편 집필 스킬로 집중](../simplification/2026-10-15-author-memory-write-only.md)을 참조한다. 이 기록의 시점별 분리와 데이터 프로토콜은 유지된다.

## Problem

`skills/story/references/author-memory.md`는 장편, 단편, AI 문체 제거, 원고 검토 네 복사본에 동기화되는 공유 참조다. 작가가 “앞으로 대화를 더 짧게 해 줘” 같은 장기 선호 하나를 말해도 에이전트는 공백 제외 8954자 전체 프로토콜을 읽어야 했다. 그중 절반 이상은 단일 책 레이아웃과 `state.book` 오류, 기존 데이터 `migrate`, 예산 추정과 조회 적재 순서, `作者画像.md`의 12288바이트 상한, “작가 메모리 정리”, 다중 이벤트 원자적 `commit`, `check`, 충돌 후보 확정, 업그레이드 전 항목처럼 드문 시점에만 필요하다. 각 스킬 진입점에는 해당 작업의 `query` 명령이 이미 있어 프로토콜의 네 행 kind 매핑 표도 중복이다.

## Decision

- `author-memory.md`는 작가가 선호 하나를 말하거나 특정 항목의 확인·교체·삭제를 요청하는 가장 흔한 시점만 다룬다. 경계·우선순위, 저장·라우팅(위치 규칙, ID 접두어 라우팅, 저장소별 이벤트 분리), 조회 해석(낮은 우선순위 성향, `omitted_ids`가 비어 있지 않으면 예산 초과, 미확정은 프롬프트 제외), 기록 여부와 기록 방식, 확인·교체·삭제와 충돌 표시, 응답 문구, `record` / `query` 명령, 단일 이벤트 형식을 유지한다. 앞부분에서 드문 시점을 나열하고 유지보수 파일로 연결한다.
- `skills/story/references/author-memory-maintenance.md`를 추가하고 `scripts/shared-references.json`에 `author-memory-maintenance-reference`로 등록한다. `author-memory.md`와 같은 네 디렉터리에 동기화한다. 기존 프로토콜에서 파일 트리, 작업 매핑 표, 주입 예산·용량(추정 기준, 적재 순서, 12288 상한), 작가 메모리 정리, 충돌 후보 확정(`replace`에 기존 항목과 후보를 함께 나열하거나 `decide=reject`), 단일 책 레이아웃, 기존 데이터 이전, 예전 항목, `init` / `commit` / `migrate` / `check`를 그대로 옮긴다.
- 조회 매핑 표를 유지보수 파일로 옮긴다. 단편·AI 문체 제거·원고 검토 진입점에는 자체 `query` 명령이 있고 장편 본문은 조립 스크립트가 대신 조회한다. 주 파일에는 “장편 설정·개요처럼 명령이 없는 작업은 `story_design` + `workflow` + `interaction`을 조회해 주 세션에만 전달”이라는 문장만 남긴다. `author_memory_commit.py`의 `--kind` 누락 오류와 예산 주석도 유지보수 파일을 가리키게 바꾼다. 런타임 복사본 다섯 개는 `sync-shared-assets.py`로 동기화한다.
- 연결 안내: story 진입점의 “작가 메모리” 절은 정리, 예산 초과, 단일 책 레이아웃 오류, 프로젝트 수준에 현재 책 항목이 남은 경우 유지보수 파일을 읽는다. story-deslop 자료 표와 story-review 참조 표에 각각 한 행을 추가한다.
- 검사: `test-author-memory-commit.py`의 “추론에 의한 저장을 유도하지 않음” 단언을 `author-memory*.md`로 확장한다. 주 파일이 유지보수 파일을 가리키고 응답·기록 절과 `record` / `query` 명령을 포함하는지 검사한다. 유지보수 파일에는 정리, 매핑 표, 단일 책 레이아웃, 이전, 충돌 후보, 12288과 드문 명령 네 개가 있어야 하며 이 규칙이 주 파일로 되돌아오면 안 된다. `scripts/doc-budget.json`의 `author-memory.md` 예산을 5450으로 등록해 분리 효과를 고정하고 드문 경로인 유지보수 파일은 등록하지 않는다.

공백 제외 글자 수: 작가가 선호 하나를 말할 때 8954 → 5353, 유지보수 파일 3964.

## Alternatives considered

- **파일을 나누지 않고 중복만 삭제**: 매핑 표와 반복 표현을 제거하면 가장 간단하고 공유 복사본도 늘지 않는다. 그러나 이전·단일 책 레이아웃·예산 추정·정리는 실제 규칙이어서 삭제할 수 없다. 주 파일이 여전히 7K 이상이며 선호 하나를 기록할 때도 전부 읽어야 하므로 채택하지 않는다.
- **세 파일로 분리(선호 기록/조회/유지보수)**: 조회 해석을 별도 문서로 만들면 선호 기록 시 약 700자를 더 줄일 수 있다. 그러나 조회 규칙은 몇 문장뿐이고 집필 중 선호 해석에서도 경계와 우선순위를 읽어야 한다. 더 나누면 장편·원고 검토 등에 연결 안내와 공유 복사본 그룹을 추가해야 해 이점보다 유지보수 비용이 크다.
- **매핑 표를 주 파일에 유지**: 기존 오류 메시지와 예산 추정 주석이 이미 이를 가리켜 런타임 스크립트를 안 바꿔도 된다. 그러나 네 행 모두 각 스킬 진입점의 구체적인 명령과 중복된다. 문자열 두 곳을 바꿔 주 파일을 “선호 하나 기록”에 더 가깝게 만드는 편이 낫다.

## Consequences

- 가장 흔한 “작가가 선호 하나 말하기”에서 약 3.6K자를 덜 읽는다. 드문 시점에는 파일 하나를 더 읽는다(주 파일 5.4K + 유지보수 4.0K, 처음 안내와 절 제목 때문에 기존보다 약 0.4K 증가).
- 공유 참조 그룹 하나가 늘고 스킬 네 개에 복사본이 하나씩 추가된다. 유지보수 규칙을 바꿀 때는 `skills/story/references/`의 원본을 수정한 뒤 `shared-references.py sync`를 실행한다.
- 주 파일 5.4K는 처음 목표인 4.5K보다 여전히 크다. 남은 이벤트 JSON 형식, 기록 판단 표, 조회 해석은 모두 해당 시점에 실제로 필요하므로 수량을 맞추려고 삭제하지 않았다.
- 충돌 후보 확정은 이전에 “직접 activate 불가”라고만 적혀 있었다. 이번에는 도구의 실제 동작과 회귀 검사에 맞춰 `replace`에 기존 항목과 후보를 함께 나열하거나 `decide=reject`를 사용한다고 명시했다.
