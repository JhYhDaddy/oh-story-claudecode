# Agent Note: 작가 기억 저장소를 프로젝트 수준·작품 수준으로 나누어 기억이 작품을 따라가도록 변경

Status: implemented
Date: 2026-09-18
Issue: #435(#429 검토 논의의 확장 A에서 파생)
Related: [2026-09-18-author-memory-query-budget](../bug-fix/2026-09-18-author-memory-query-budget.md), [2026-09-18-author-memory-explicit-only](../simplification/2026-09-18-author-memory-explicit-only.md), [2026-09-24-author-memory-single-root](../bug-fix/2026-09-24-author-memory-single-root.md)(작품 루트가 작업 공간 자체이면 작품 수준 저장소는 `书级/` 하위 디렉터리 사용)

## Problem

이전 작가 기억은 ‘작업 공간마다 하나’였다. 작품 A·B의 book 항목과 전역 항목이 `{工作区}/.story/作者记忆/`의 state 하나에 섞였다. 그 결과 다음 문제가 생겼다.

1. 작품을 보관·이전하거나 다른 작업 공간으로 복사해도 선호는 원래 작업 공간에 남아 고립된다. 작업 공간 하나의 저장소만으로는 해결할 수 없다.
2. 쓰기 측 예산 알림은 ‘가장 무거운 작품 선택’으로 최악의 경우만 추정할 수 있다(#429의 5항에서 이미 두 측정 기준을 맞춤). 작품 수준 항목을 쓸 때 ‘해당 작품 + 전역’은 여전히 정확한 계산이 아니라 추정이다.

작품 수준 데이터를 작품 디렉터리에 두는 것은 저장소의 기존 관례(`追踪/`, `设定/`)이며 작가 기억만 예외였다.

## Decision

1. **2단계 저장소**: 프로젝트 수준 `{工作区}/.story/作者记忆/`에는 global / genre / workflow 항목만 저장하며 ID 접두사는 `AP`다. 작품 수준 `{书}/.story/作者记忆/`에는 해당 작품의 book 항목만 저장하며 접두사는 `BP`다. state에 작품명을 기록하는 `book` 필드 하나를 추가한다. 두 수준의 디렉터리 구조·파생 뷰·트랜잭션 형식은 완전히 같으며 `validate_state`가 저장소별 접두사와 scope 귀속을 검증한다.
2. **ID 접두사가 라우팅 키**: `decide` / `forget`은 `item_id` 접두사를 보고 `remember` / `replace`는 `scope.level`을 본다. 작품 수준 작업은 반드시 `--book-root {书目录}`를 전달해야 하며 빠뜨리면 즉시 오류를 낸다. 프로젝트 수준에 대신 기록하지 않는다. 그렇게 허용하면 기존 항목을 영원히 정리할 수 없기 때문이다. `commit` 하나는 저장소 하나만 쓴다. `replace`와 `conflicts_with`는 저장소를 넘나들지 않는다. 해당 작품의 예외가 우선순위에 따라 전역을 덮는 것은 충돌로 보지 않으며 저장소를 옮기는 변경은 `forget` + `remember`로 나눈다.
3. **작품명은 state 기준**: 처음 생성할 때 `--book` 또는 디렉터리 이름을 쓰며 이후 디렉터리 이름이 바뀌어도 영향을 받지 않는다. `--book`이 state 기록과 다르면 오류를 낸다.
4. **조회는 프로젝트·작품 수준 병합**: `query --book-root`는 두 수준을 읽어 중요도 → 해당 작품 예외 → 최근 갱신 순으로 병합해 채운다. 두 저장소의 리비전 번호는 서로 비교할 수 없지만 book 항목은 작품 수준에서만, 나머지는 프로젝트 수준에서만 나오므로 같은 scope는 반드시 같은 저장소다. 따라서 ‘최근 갱신’은 리비전 번호로 비교해도 된다. `--book-root`를 전달하지 않으면 해당 작품 항목을 전혀 얻을 수 없다.
5. **예산 알림**: book 범위는 현재 보이는 작품 수준 저장소 자체이므로 더 이상 ‘가장 무거운 작품’을 고를 필요가 없다. 작품 수준 항목을 쓸 때 ‘해당 작품 + 전역’을 정확히 계산한다. 프로젝트 수준 항목을 쓸 때는 작품 수준 저장소가 보이지 않지만 `--book-root`를 함께 전달하면 현재 작품을 계산에 포함한다. 추정과 실제 조회는 모두 `build_query_result`로 전달 구조를 만든다(`book_revision`도 포함). 검토에서 추정 측이 추가 필드를 빠뜨려 초과를 놓치는 경우를 재현했다. `assert_no_false_negatives`의 기준 판정은 `merged_query`(`command_query`가 사용하는 순수 함수)를 직접 호출하도록 바꾸고 테스트 안에 조회를 다시 구현하지 않는다. 그렇지 않으면 기준 판정과 추정이 같은 잘못된 근거에 의존해 전달 구조의 불일치를 검출할 수 없다. 변이 검증에서 추정 측의 extra를 제거하면 테스트가 실패한다.
6. **기존 항목은 이전만 하고 이중 조회하지 않기**: 업그레이드 전 프로젝트 수준에 기록한 book 항목은 조회·추정에 더 이상 참여하지 않으며 새 book 쓰기도 받지 않는다. 프로필에는 계속 보이고 `decide` / `forget`은 가능하다. `migrate --book-root`가 한 번에 전체 묶음을 옮긴다. 진술·근거·확인 횟수·중요도를 그대로 보존하고 `BP` 번호로 바꾸며 원래 `AP`는 `superseded`로 표시하고 목적지를 기록한다. 작품 수준에서는 **원본 항목마다 트랜잭션 하나**인 `migrate:APxxx`를 사용하며 다이제스트에는 불변 필드(번호·유형·범위·진술)만 넣는다. 검토에서 전체 묶음에 하나의 트랜잭션 번호를 쓰고 다이제스트에 status / evidence를 포함하면, 중간 실패 후 작가가 기존 항목에 `decide` / `forget`을 수행했을 때 영구 잠김(같은 번호·다른 다이제스트)이나 중복 생성(묶음이 바뀌어 새 번호)이 생긴다고 지적했다. 작품 수준을 먼저 쓰고 프로젝트 수준을 나중에 쓴다. 재실행 시 작품 수준에 기록이 있으면 그 번호를 재사용하고 프로젝트 수준만 보완한다. 실패 구간에서 원본에 수행한 `decide` / `forget`은 사본에 동기화되지 않으므로 작가가 사본에 다시 수행해야 한다. 재실행은 작품 수준 스냅샷도 다시 써 파생 뷰를 복구한다. 전역 항목과의 충돌 관계는 이전 후 성립하지 않으므로 해당 후보는 `pending`으로 되돌린다. ‘작가 기억 정리’의 기본 제안 항목에 이전을 넣는다.
7. `fingerprint`의 `scope.value` 비교를 casefold로 바꾸어 `same_scope_value`·부분 목록 병합과 기준을 맞춘다. 이제 작품명은 `--book`·디렉터리명·state 세 곳에서 올 수 있으므로 대소문자가 다르다고 두 번째 항목을 파생시키면 안 된다.
8. 호출 지점: story-review / story-deslop / story-short-write의 `query`는 `--book-root`를 명시적으로 전달한다. story-long-write 진입점에도 `--book-root` 포함을 명시한다. 스크립트·문서 사본 다섯 개는 `sync-shared-assets.py` / `shared-references.py`로 동기화한다.

## Alternatives considered

**종료 시점 없이 영구 이중 조회.** 기존 사용자가 아무것도 하지 않아도 되어 이전 비용이 없다는 점이 가장 큰 장점이다. 그러나 #429 검토는 이 경로가 ‘오랫동안 남아 아무도 정리하지 않을 가능성이 가장 높다’고 명시했다. 조용한 호환이 지속되면 이전도 영원히 일어나지 않고 고립 문제도 해결되지 않으므로 채택하지 않는다.

**호환 조회와 매번 항목을 명시하는 종료 알림(이번 첫 버전, 철회).** 기존 항목을 그대로 반환하고 `query`의 `legacy_book_ids`에 항목을 명시하며 쓰기마다 `warnings`에서 작품별로 집계해 이전이 끝날 때까지 알린다. 업그레이드로 선호가 사라지지 않는 장점이 있다. 그러나 추정 시 기존 부분 목록과 작품 수준 저장소를 합쳐야 하고, 저장소 간 정렬은 제출 시각을 비교해야 하며, `migrate`는 실패 구간에서 종료된 원본 항목의 부활 문제까지 처리해야 한다. 호환 경로만 약 150줄 늘었다. 사용자가 복잡도가 너무 높다고 판단해 철회하고 이전만 하되 조회하지 않는 방식으로 바꿨다. 업그레이드 후 작품 선호는 `migrate`를 한 번 실행해야 돌아온다고 UPGRADING에 명시한다. 전역·장르·작업 흐름 선호에는 영향이 없다.

**작품 수준 저장소는 `scope.value` 없이 디렉터리로만 식별.** 중복 필드 하나를 줄일 수 있다. 그러나 `compact_item`은 집필자가 ‘현재 작품’ 범위를 볼 수 있어야 하는 주입 계약이며 작품 디렉터리 이름을 바꾸면 작품명을 기록할 곳도 없어진다. state에 `book` 필드 하나를 추가하는 편이 계약 변경보다 비용이 적어 채택하지 않는다.

**저장소를 넘는 `replace` / `conflicts_with`.** ‘이 작품 규칙으로 전역 규칙 대체’를 한 단계로 할 수 있다. 그러나 두 저장소는 각각 원자적으로 제출해 저장소 간 참조의 일관성을 보장하지 못한다. 기존 우선순위 설계상 작품 예외가 전역 규칙을 supersede해서도 안 되므로 채택하지 않는다.

**`--book-root`가 없으면 `--book`으로 `长篇/`, `短篇/` 아래 디렉터리 추측.** 인자 하나를 덜 전달할 수 있다. 그러나 작품 디렉터리 배치는 스킬별로 정하며 `.active-book`은 어떤 상대 경로든 가리킬 수 있다. 스크립트가 틀리게 추측하면 기억을 잘못된 디렉터리에 조용히 기록하므로 매핑은 호출자가 전달하고 추측은 에이전트에 맡긴다.

## Consequences

- 작품 보관·이전·복사 시 선호가 함께 이동하며 작품 수준 항목을 쓸 때 예산 알림도 최악의 추정에서 정확한 계산으로 바뀐다.
- 호환성을 깨는 변경: book 수준 `record` / `commit`에 `--book-root`가 없으면 즉시 오류가 난다. 옛 스킬 사본의 호출 지점은 `/story-setup`을 다시 실행해 갱신해야 한다. CHANGELOG `Changed`에 기록한다.
- 기존 작업 공간을 업그레이드하면 작품별로 `migrate`를 실행할 때까지 해당 작품 선호가 prompt에서 사라진다. UPGRADING과 CHANGELOG 모두 이 단계를 명시한다.
- 프로젝트 수준 항목을 쓰면서 `--book-root`를 전달하지 않으면 알림이 작품 수준 저장소를 전혀 보지 못해 특정 작품의 예산 초과를 놓칠 수 있다. 작품 수준 쓰기에서는 이를 보완해 알린다. 문서는 특정 작품을 집필 중이면 항상 `--book-root`를 전달하도록 요구한다.
- 작품 디렉터리를 포함하는 `query` 페이로드에는 `book_revision`이 추가되어 2048바이트 전달 구조에 포함되며 추정 측도 똑같이 계산한다.
- `migrate` 중간 실패 구간에서 원본에 수행한 `decide` / `forget`은 이미 만든 사본에 동기화되지 않는다. 재실행은 잠기거나 중복 항목을 만들지 않지만 사본 상태는 작가가 직접 다시 처리해야 한다.
- 작품 하나를 이전하면 작품 수준 journal에 항목마다 트랜잭션 하나가 남는다. 변경 기록 뷰는 최근 100건만 보여 주므로 기존 항목이 수백 개인 작품은 더 오래된 기록을 뷰 밖으로 밀어낸다(state에는 모두 남음).
