# Agent Note: 35K 상한 아래에 문구 수정 여유 확보

Status: implemented
Date: 2026-09-27
Related: [35K 로드 상한](../architecture/2026-09-26-per-call-load-ceiling-35k.md), [예산 중첩 등록](../architecture/2026-09-26-budget-stacking-and-solo-reads.md), [AI 문체 제거 등급 판정 통합](../bug-fix/2026-09-27-deslop-one-grading.md)

## Problem

v0.8.2 마무리 시점에 자주 쓰는 경로 몇 개가 35K에 바짝 붙어 있었다. 장편 일일 집필에서 주 세션이 직접 쓰는 최악의 중첩은 265자, 단일 장은 1.4K 미만만 남았다. 주 세션이 직접 AI 문체를 제거하는 경로는 181자, 한 명이 분할 검토하는 경로는 154자, 단편 작품 분석에서 기법 표를 조회하는 경로는 108자만 남았다. 문장 하나를 바꾸려 해도 먼저 다른 곳에서 글자를 삭제해야 했고, 변경이 수량을 맞추기 위한 삭제로 흐르기 쉬웠다.

## Decision

“이번 호출에서 쓰지 않는” 텍스트만 이동하거나 잘못 측정한 등록값을 실제 읽기 방식에 맞춘다. 본문 집필에 필요한 규칙은 삭제하지 않는다.

- **장편 본문 집필**: 파일 누락과 추적 불일치 수정법(원래 workflow-chapter 앞부분과 workflow-daily Step 1)은 새 파일 `stop-and-fix.md`로 옮기고, 멈춰서 수정하며 이번 실행에서 집필하지 않을 때만 읽는다. 일일 집필의 “자주 묻는 문제” 표를 삭제한다. 네 행 모두 본문 절차나 진입부와 중복이며, 유일하게 독자적인 “권말에 새 권을 시작할지 묻기”는 묶음 작업 종료 보고 템플릿에 합친다. “더 쓸 수 없음”을 알리는 질문은 workflow-chapter에 남긴다. 집필 후 도구를 쓸 수 없거나 퇴화 문제를 두 번 수정해도 실패하면 같은 집필 호출에서 사용해야 하기 때문이다.
- **AI 문체 제거**: narrative-writer에 넘기는 프롬프트 전체를 `story-deslop/references/agent-calls.md`로 옮기고 주 세션이 직접 수정할 때는 읽지 않는다. 두 등급 판정 기준을 하나로 합치면서 중복도 줄인다(관련 기록 참조).
- **단독 원고 검토**: solo.md는 원래 anti-ai-writing의 “AI写作指纹”(AI 집필 지문)와 “10 种 AI 写作模式检测”(AI 집필 패턴 10종 검사) 두 절만 읽도록 했으나 예산은 파일 전체로 계산했다. 두 절만 계산하도록 바꾼다.
- **단편 작품 분석 Stage 4–6**: 진입부에 집필 기법 중 “感情线四阶段推进法”(감정선의 네 단계 전개법) 제목만 찾아 읽는다고 명시한다. 예산은 원래 전체 파일을 상한으로 계산했으나 이 절만 계산하도록 바꾼다.
- **새 책 첫 장의 추적 초기화**: 비교 집필에서 새 책 첫 장은 먼저 tracking-initialization을 읽어 추적을 초기화하는데, 이 파일은 이전에 어느 경로에도 등록되지 않았다. “새 책에 추적 정보가 없으므로 먼저 초기화”는 본문 집필의 정상 단계이므로 workflow-chapter 앞부분에 남긴다. “본문은 있는데 추적 정보가 없음”만 stop-and-fix로 옮긴다. tracking-initialization은 각 “새 책 첫 장” 분기에 추가한다.

결과(공백 제외 글자 수, 35K까지의 여유): 장편 일일 집필 주 세션 직접 작성의 최악 중첩은 34,459자(541자 여유), 파일 누락 분기는 506자 여유다. 단일 장 solo 최악 중첩은 34,408자(592자 여유, 추가 등록한 초기화 파일 포함)다. 주 세션 직접 AI 문체 제거는 846자, 단독 분할 검토는 약 7.1K, 단편 작품 분석의 기법 표 조회는 약 7.6K가 남는다. 변경 경로의 예산은 실제 사용량에 맞춰 다시 고정한다.

## Alternatives considered

- **writing-craft의 가끔 사용하는 절(숫자 서사, 관통 소품, 도입부 밀도)을 조건부 읽기로 이동**: 한 번에 2~3천 자를 확보할 수 있다는 장점이 있다. 그러나 writing-craft는 집필자와 주 세션이 매 장 읽는다. 옮기면 일반 집필에서 읽는 규칙이 바뀌므로 별도 비교가 필요하다. 이번에는 집필에 영향을 주지 않는 텍스트만 변경한다.
- **드문 시점의 작가 질문(분량 범위 이탈, 결정을 받아야 할 새 요소)을 workflow-chapter 밖으로 이동**: 약 천 자를 아낄 수 있다. 그러나 이 질문은 집필 후 같은 호출 안에서 발생하므로 다른 파일로 옮겨도 최악 조건에는 중첩된다. 일반 경로에서 아낀 글자도 최악 중첩에서는 전부 다시 포함된다.
- **예산을 직접 상향**: 35K는 절대 상한이므로 조정할 여지가 없다.

## Consequences

- 이점: 장편 본문 집필, AI 문체 제거, 원고 검토, 단편 작품 분석의 가장 빠듯한 경로에 모두 500자 이상의 여유가 생겨 다음 버전의 규칙 수정 때 먼저 글자를 삭제하지 않아도 된다. 원고 검토와 단편 작품 분석은 이전의 과다 계산을 실제 읽기 방식에 맞췄다.
- 비용: 장편에 `stop-and-fix.md`, AI 문체 제거에 `agent-calls.md`가 하나씩 추가되므로 수정법과 프롬프트 위치를 알아야 한다. 파일 누락 분기는 파일 하나를 더 읽어 약간 늘었다. 단편 본문 집필의 가장 무거운 조합은 여전히 324자만 남지만 이번에는 바꾸지 않았다. 같은 시기에 단편 대화 교체 비교를 진행하고 있어 해당 텍스트를 유지했다.
