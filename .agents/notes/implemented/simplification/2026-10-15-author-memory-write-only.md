# Agent Note: 작가 기억을 장편·단편 집필 스킬에 집중

Status: implemented
Date: 2026-10-15
Related: [스킬 간 실제 사본 유지](../architecture/2026-05-07-cross-skill-copies-not-symlinks.md), [작가 기억의 2단계 저장소](../architecture/2026-09-18-author-memory-two-level-store.md), [작가 기억을 사용 시점별로 분리](../architecture/2026-09-26-author-memory-by-moment.md)

## Problem

작가 기억의 프로토콜과 트랜잭션 스크립트가 story 라우터, 장편 집필, 단편 집필, AI 문체 제거, 원고 검토의 다섯 곳에 동시에 존재했다. 따라서 진입점과 텍스트 처리 작업이 각각 선호 조회·기억 관리·쓰기 책임을 맡았다. 유지 관리자는 기능을 보존하면서 책임을 write 스킬에 집중하라고 요청했으며 기억 기능을 삭제하라고 한 것은 아니다.

## Decision

작가 기억 관리·조회·쓰기는 story-long-write와 story-short-write에만 유지한다. 장편 집필을 공유 원본으로 삼고 단편에는 독립 설치에 필요한 실제 사본을 남긴다. 습관 관리만 요청하면 관리 후 중단하고, 집필도 요청하면 해당 집필 흐름을 계속한다. story는 작품 유형에 따라 관리 요청을 라우팅할 뿐이며 AI 문체 제거와 원고 검토는 기억에 독립적으로 접근하지 않고 앞선 집필 흐름에서 내린 문체 결정을 따른다. 단독 호출 시 현재 요구와 해당 작품의 문체를 사용한다. 2단계 저장소, 처리 확인서, 기존 집필 시 기억 불러오기, 데이터 형식은 유지한다. 각 호스트 프로젝트 지침, 공유 목록, 예산, 테스트, 공개 설명을 함께 갱신한다.

## Alternatives considered

- 작가 기억을 완전히 제거하면 모든 프로토콜·런타임 비용을 없앨 수 있다. 그러나 기능을 유지하라는 요구와 맞지 않아 철회했다.
- 모두 story에 집중하면 관리 진입점이 하나라 사본을 가장 줄일 수 있다. 그러나 라우터 스킬이 창작 상태를 맡게 되어 write에 귀속하라는 명시적 요구와 어긋난다.
- 장편·단편이 스킬 간 파일을 공유하면 실제 파일 하나만 남길 수 있다. 그러나 기존 독립 설치 계약을 깨므로 명시적 목록으로 관리하는 실제 파일 두 개를 사용하고 다른 스킬의 사본은 제거한다.

## Consequences

기억 구현을 다섯 곳에서 두 집필 진입점으로 줄이면서 세션 간 습관과 기존 조회 능력을 보존한다. 대신 단독 원고 검토나 AI 문체 제거는 작가 기억을 자동으로 불러오지 않고 현재 요청, 작품 문체 또는 집필 호출자의 판단이 필요하다. 과거 선호 데이터를 옮길 필요는 없으며 장편·단편 사본의 일치는 공유 검사가 계속 보장한다.

## 검증

작가 기억 트랜잭션 동작 회귀, 집필 파이프라인 CLI 회귀 42개, 문체 회귀 7개를 통과했다. 정적 구조, 번호, 자주 로드되는 문서 예산, 공유 사본과 소비 경로 도달성, 현재 계약, 호스트 어댑터·배포 검사를 통과했다. 장편·단편 트랜잭션 스크립트와 장편 자동 작업 묶음 생성 코드는 원문을 유지하고 귀속·라우팅·후속 실행자의 수신 경계만 조정했다.
