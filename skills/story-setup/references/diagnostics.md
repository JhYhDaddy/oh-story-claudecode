# 집필 환경 점검만 수행

`story-setup check`, ‘집필 환경 확인’, ‘에이전트를 쓸 수 없는 이유’ 같은 진단 요청에 사용한다. 검사와 보고만 하며 파일 복사·설정 수정·배포 표식 생성·배포/마이그레이션/커밋 명령을 실행하지 않는다. 사용자가 수리를 요청했다면 발견 사항부터 나열하고 `story-setup/SKILL.md`의 기존 배포 절차와 호스트별 `references/deploy-*.md`로 처리한다.

## 1. 점검 대상 결정

사용자가 지정한 프로젝트 루트를 우선한다. 없으면 현재 디렉터리에서 위로 가장 가까운 `.story-deployed`를 찾는다. 없으면 ‘배포 표식을 찾지 못해 배포 상태를 확인할 수 없다’고 보고하고 기존 파일과 실행 환경만 점검한다. 이를 근거로 자동 초기화하지 않으며 무관한 프로젝트는 탐색하지 않는다.

`.story-deployed`의 대상 호스트·버전·참조 경로를 읽는다. 여러 대상은 각각 확인한다. 필드 누락·해석 불가·알 수 없는 대상은 구체적으로 기록하며 호스트를 추측해 쓰지 않는다. `agents_version`을 현재 `story-setup/SKILL.md`와 비교한다. 로컬 패키지가 더 오래되었으면 먼저 갱신하고 낮은 버전으로 재배포하지 않는다.

## 2. 배포 검증 재사용

대상별 `references/deploy-{target_cli}.md`의 배포 목록과 검증 절(해당 대상 문서만 읽음), `story-setup/SKILL.md` Phase 3의 배포 표식 검사를 따른다. 대상 파일을 하나씩 읽고 읽기 전용 검증을 수행한다. 스킬·에이전트·훅 목록은 배포 문서를 재사용한다.

- 설치된 스킬 패키지와 프로젝트 배포 사본을 구분한다. Claude Code·Codex·OpenCode 프로젝트 경로는 주로 에이전트·훅·참조를 저장하며 모든 `SKILL.md`가 있을 필요는 없다. 다른 호스트는 각 배포 목록을 따른다. skills-only 호스트에 네이티브 에이전트/훅이 없는 것은 정상이다.
- 참조 자료는 하위 디렉터리를 포함한 소스의 상대 파일 목록과 하나씩 대조한다. 디렉터리가 비어 있지 않거나 파일 수가 같다는 것만으로 완전성을 입증할 수 없다. 소스를 사용할 수 없거나 소스와 대상이 같으면 독립적으로 완전성을 검증할 수 없다고 설명하고 통과로 처리하지 않는다.
- 훅의 파일 존재뿐 아니라 설정 등록과 스크립트 의존성도 확인한다. 배포 문서의 구문·해석·등록 검증을 사용하며 프로젝트에 쓸 가능성이 있는 훅을 임의 실행하지 않는다.
- 파일 존재는 배포 파일 준비만 뜻한다. 현재 세션의 custom agents 로드와 훅 신뢰 여부는 호스트가 실제 노출한 기능·보이는 상태로 판단한다. 확인할 수 없으면 ‘미검증’으로 기록한다. 파일만 보고 호출 가능하다고 하거나 점검을 위해 집필 작업을 시작하지 않는다.

## 3. 실행 환경과 추적

`node --version`을 실제 실행한다. Python은 플랫폼 공통 규칙에 따라 `python3`·`python`·`py` 순으로 탐색하고 버전을 실행 확인하여 Python 3인 인터프리터를 사용한다. 명령이 존재해도 실행하지 못하면 통과가 아니다. 없으면 영향을 받는 구체적 스크립트를 설명한다. 의존성을 자동 설치하거나 모델 호출·온라인 인증을 하지 않는다.

장편 프로젝트를 점검한다면 사용자 지정 작품·`.active-book`·기존 `추적/`로 작품 루트를 정한다. 현재 디렉터리가 작품 루트인 구조와 `장편/{书名}/` 구조를 지원한다. 장편 프로젝트가 없으면 추적 검사를 건너뛰고 경고하지 않는다.

설치된 `story-long-write` 스킬의 기존 검증기를 사용한다.

```bash
"$PYBIN" -B "{story-long-write skill目录}/scripts/tracking_commit.py" check --project "{书根}"
```

`PYBIN`은 앞에서 실행 확인한 Python 3다. 이 `check`는 추적 상태와 파생 뷰를 검증한다. ‘JSON 해석 가능’으로 대체하지 않는다. 인터프리터·검증기·의존성이 없으면 검사를 마치지 못했다고 보고한다. 간소화한 검증기를 새로 쓰거나 `init` / `commit`으로 수리하지 않는다. 추적 문제는 `UPGRADING.md`의 마이그레이션 설명과 기존 추적 트랜잭션 절차를 따른다.

## 4. 보고와 후속 조치

독자는 프로그래밍을 모르는 작가다. 먼저 집필 용어로 ‘지금 쓸 수 있는 것’(정상 집필 기능을 한 문장으로)과 ‘해야 할 일’(새 세션 열기, Codex의 /hooks에서 신뢰하기처럼 바로 따라 할 항목; 없으면 조치 불필요) 두 단락을 쓴다. 이 두 단락에는 스크립트명·필드명·상태명·파일 경로를 넣지 않는다. 그다음 ‘발견한 문제’·‘미검증 항목’으로 기술 세부를 모아 대상 호스트/작품·경로/명령 결과·구체적 영향·다음 단계를 제시한다. 정상 결과는 요약하고 skills-only의 예정된 제약을 설치 실패로 표현하지 않는다. 결론에는 실제로 검증한 기능을 명시한다.

배포 파일 보충이 필요하면 `story-setup` 재실행을 권한다. 소스 패키지가 없거나 프로젝트보다 오래되면 먼저 갱신한 뒤 배포한다. 현재 세션에서 기능을 읽지 않았으면 새 세션이나 해당 CLI의 신뢰 절차를 안내한다. 점검만 요청했다면 여기서 끝내고 경고를 없애려고 임의로 수리하지 않는다.
