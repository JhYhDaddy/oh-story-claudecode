# Agent Note: 프로젝트 지침 템플릿에 작가 협업 규칙 추가: 작가 메모리 라우팅, 설치 스킬 보호, 집필 용어로 설명

Status: implemented
Date: 2026-09-24
Related: [2026-09-18-author-memory-explicit-only](../simplification/2026-09-18-author-memory-explicit-only.md), [2026-09-18-author-memory-two-level-store](../architecture/2026-09-18-author-memory-two-level-store.md)

## Problem

출시 전 실제 Claude Code 세션을 재확인하면서 세 가지를 발견했다.

- 작가가 “기억해 줘. 이 책의 대화에는 낫표를 써”라고 직접 말했는데 두 번 모두 Claude Code의 auto memory(`~/.claude/projects/.../memory`)에 들어가고 oh-story의 작가 메모리에는 들어가지 않았다. 명시적인 `/story 记住`만 동작했다. 기록 규칙은 작가가 명시한 내용만 저장하도록 이미 정리했다(Related 참조). 이 경로가 유일한 쓰기 진입점이므로 신뢰할 수 있어야 한다. 호스트 시스템 지침 자체가 “사용자가 기억하라고 하면 즉시 저장”하도록 요구하므로 프로젝트 지침에 라우팅을 적지 않으면 모델은 호스트 메모리를 먼저 사용한다.
- `author_memory_commit.py` 오류가 나자 모델은 집필 프로젝트에 설치된 스킬 스크립트를 수정해 오류를 우회하고 작가에게 “최소한으로 수정했습니다”라고 말했다. 설치된 스킬 파일은 story-setup이 관리하며 다음 배포 때 덮어쓴다. 우회한 오류가 작가에게 알려야 할 데이터 문제일 수도 있다.
- 배포 보고, 검사 보고와 일상 답변에 스크립트 이름, 필드 이름, 상태 이름이 자주 등장했다. 유지보수자는 프로그래밍을 모르는 작가에게는 집필 용어로 설명하라고 요구했다.

## Decision

- 사용자 프로젝트에 배포하는 지침 템플릿에 “작가와 협업” 절을 추가한다. 중국어 템플릿에서는 “Compact 후 컨텍스트 복구” 앞에 두며 Antigravity 규칙에서는 영어 `## Working with the author`를 쓴다. 규칙은 세 가지다.
  1. 답변과 보고는 집필 용어로 작성하고 작가에게 스크립트·필드·상태 이름을 던지지 않는다. 오류 보고 때만 원본 오류를 첨부한다.
  2. 작가가 집필 습관·선호를 기억하거나 잊거나 확인하라고 하면 story 스킬의 “작가 메모리”로 보내 해당 스크립트가 `.story/作者记忆/`에 쓰게 한다. 코딩 도구의 메모리(예: auto memory)에는 저장하지 않는다. 일회성 요구는 그대로 수행하고 기록하지 않는다.
  3. 프로젝트에 설치된 스킬 파일(`SKILL.md`, `references/`, `scripts/`)을 수정하지 않는다. 스킬 스크립트가 오류를 내면 멈추고 오류와 실행 명령을 작가에게 알리며 임의로 고쳐 우회하지 않는다.
- 대상 템플릿: `templates/CLAUDE.md.tmpl`(OpenCode의 `AGENTS.md.tmpl`은 `sync-opencode.py`로 생성), `codex` / `zcode` / `openclaw` / `reasonix` / `generic`의 `AGENTS.md.tmpl`, `antigravity/rules/oh-story.md`.
- story-setup 설치 보고와 `check` 진단 보고는 먼저 “지금 할 수 있는 일”과 “추가로 해야 할 일”을 집필 용어로 설명하며 경로·필드 이름을 내세우지 않는다. 파일 목록 등 기술 세부 사항은 끝의 짧은 “배포 내역”에 둔다.
- 템플릿 변경은 `agents_version` 31과 함께 배포하며 이미 배포한 프로젝트에서는 story-setup을 다시 실행해야 적용된다.

## Alternatives considered

- **story 스킬 트리거 설명만 바꿔 “기억해 줘”가 더 쉽게 연결되도록 함** — 배포 템플릿을 건드리지 않아 배포 비용이 없고 해당 스킬에서 직접 고칠 수 있다. 그러나 실측 문제는 story가 호출되지 않는 것이 아니라 호스트 시스템 지침의 메모리 명령이 먼저 실행되는 것이었다. 항상 컨텍스트에 있는 프로젝트 지침만 경쟁할 수 있으며 스킬 설명으로는 해결되지 않는다.
- **훅으로 호스트 메모리 디렉터리 쓰기 차단** — 모델이 문구를 따르는지와 무관하게 결정적으로 처리할 수 있다. 그러나 호스트별 메모리 저장 위치와 도구가 다르다. Claude는 `~/.claude/projects/.../memory`에 쓰지만 다른 호스트는 각자 방식이 있거나 메모리가 없다. 일곱 호스트별 차단기를 만드는 비용이 크고 프로젝트 밖 쓰기는 기존 훅의 책임 범위도 아니다.
- **설치 스킬 수정을 허용하되 사후 보고 의무화** — 작가가 유지보수자의 배포를 기다리지 않고 집필을 계속할 수 있다. 그러나 다음 story-setup에서 패치가 조용히 덮어써져 같은 오류가 재발한다. 모델이 우회하는 오류는 메모리 항목 충돌 같은 작가 데이터 문제인 경우도 많아 작가가 원본 오류를 보고 판단해야 한다.
- **세 규칙을 각 스킬의 SKILL.md에 작성** — 규칙이 스킬을 따라가며 배포에 의존하지 않는다. 그러나 “기억해 줘” 라우팅은 story 스킬이 로드되기 전에 발생하므로 항상 로드되는 프로젝트 지침에 있어야 한다. SKILL.md 13개에 쓰면 자주 읽는 경로의 예산도 소모한다.

## Consequences

- **이점**: 배포된 프로젝트에서 단순히 “기억해 줘: …”라고 해도 작가 메모리로 연결된다. 스킬 스크립트 오류를 작가에게 그대로 보여 주고 비개발자도 보고를 이해할 수 있다.
- **비용**: 세션별 프로젝트 지침이 약 200자 늘며 기존 프로젝트는 story-setup을 다시 실행해야 새 템플릿을 받는다.
- **알려진 한계**: 세 규칙 모두 문구상의 제약이므로 모델이 따르지 않을 수 있다. 실제 모델의 라우팅 동작을 검증하는 자동 테스트는 없다. 호스트 메모리 시스템 지침이 더 강하면 여전히 먼저 실행될 수 있다. 실제 세션에서 “기억해 줘:” 한 문장이 `.story/作者记忆/`에 들어가는지 재검증해야 한다.
