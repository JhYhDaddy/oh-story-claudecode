# Agent Note: 작가 메모리 주입 예산을 읽을 때의 조용한 잘림에서 쓸 때의 사전 경고로 변경

Status: implemented
Date: 2026-09-18
PR: #429
후속: [집필자가 읽는 행으로 주입 예산 측정](../architecture/2026-10-09-author-memory-budget-on-writer-text.md)(2048 유지, 측정 대상을 JSON 포장에서 `lines`로 변경, `omitted_ids` 상한 제거)

## Problem

`query` 출력은 집필 에이전트 프롬프트에 그대로 붙인다. `QUERY_MAX_BYTES = 2048`은 프롬프트 안의 주의력 예산이며 #368에서 설계했으므로 늘리면 안 된다. 그러나 예산은 읽을 때만 적용됐다. 항목이 쌓이면 작업 조합별 조회에서 조용히 잘려 작가는 `record` 응답을 보고 기억했다고 생각하지만 실제로 해당 항목이 프롬프트에 영영 들어가지 않을 수 있고 징후도 없었다. 기존 `omitted > 0` 안내인 “kind를 좁혀 재조회”는 필터 불일치가 아니라 예산 때문에 밀려난 상황에서 오해를 준다.

## Decision

주입 예산 때문에 쓰기를 실패시키지는 않되 **사전에 경고**하고 버려지는 내용을 예측·확인할 수 있게 한다.

1. `record` / `commit`은 `warnings`를 반환한다. `references/author-memory.md` 매핑 표의 네 작업 조합으로 최악의 조회(전역 항목＋각 scope 차원에서 가장 무거운 단일 부분집합)를 추정한다. 다 담지 못하는 조합에서 제외될 항목과 **그 단언의 첫 문장**을 지목한다. 쓰기는 정상 성공한다.
2. 추정과 실제 조회는 같은 기준을 쓴다. 부분집합은 `casefold`로 병합해 `same_scope_value`와 맞추고 무게는 JSON 배열 구분자까지 포함한 `compact_bytes + 2`로 센다. 둘 중 하나라도 다르면 응답은 괜찮다고 하지만 다음 query에서 누락되는 거짓 음성이 발생한다.
3. 적재 순서는 **중요도 → 현재 책 예외 → 최근 갱신 → 확인 횟수 → 번호**다. 중요도는 scope보다 앞서야 한다. scope가 앞이면 아무리 많은 `low` 책별 사소한 항목도 `high` 전역 필수 규칙을 밀어낼 수 있다.
4. 다 담지 못하는 항목은 건너뛰되 중단하지 않는다. 긴 항목 하나가 뒤의 짧은 항목을 막지 않게 한다. 빠진 ID는 **후보 우선순위**로 정렬해 `omitted_ids`에 보고한다(최대 20개, `omitted`에는 실제 총수 유지). 버린 순서로 정렬하면 마지막 정리에서 다시 제외된 높은 우선순위 항목이 상한 밖으로 잘릴 수 있다.
5. 새 항목의 `assertion`은 120바이트로 제한하되 **기존 항목 강화에는 적용하지 않는다**. 그렇지 않으면 기존 긴 단언을 다시 확인할 수 없어 오래된 선호 재확인이 중복 항목을 만들고 라이브러리가 더 붐빈다.
6. `query --kind`를 필수로 바꾸고 매핑 표에서 유형을 선택한다.
7. `作者画像.md`에 `importance`를 표시한다. 예산 초과 시 유지·제외 판단 기준인데 “작가 메모리 정리”는 이 파일만 입력으로 사용하므로 표시하지 않으면 폐기할 항목을 판단할 수 없다.
8. 문서는 **선호 하나를 기록 하나로 쓰고 예외·한정을 별도 항목으로 분리하지 말라**고 요구한다. 개별 삭제와 항목 분리가 겹치면 예외만 사라져 “X가 아니면 Y를 하지 않음”이 본문에 전달되는 절대 금지로 바뀔 수 있다.

불변 조건은 `assert_no_false_negatives`(고정 시드 무작위 라이브러리에서 “응답 경고 없음 ⟹ 모든 실제 query에서 누락 없음” 전수 검사), `assert_slice_weight_counts_separators`, `assert_omitted_ids_follow_priority` 회귀 검사로 고정한다.

## Alternatives considered

**초과 시 쓰기 거부(이 PR 초안 ef5b504, 폐기).** 저장할 수 있으면 반드시 프롬프트에도 들어간다는 구조적 보장이 가장 큰 장점이다. 작가는 거짓 응답을 받지 않아 어떤 경고보다 강하다. 그러나 트랜잭션 후 상태에 `enforce_query_budgets(updated)`를 무조건 호출하여 교착된다. 이미 예산을 넘은 기존 라이브러리는 순수 `forget`도 거부되어 하나씩 줄일 수 없고 state를 직접 고쳐야 하므로 채택하지 않는다.

**트랜잭션이 상황을 악화할 때만 쓰기 거부.** 전후 누락 수를 비교해 늘지 않으면 허용하면 줄이는 작업은 통과하고 새로 상한을 넘기는 추가만 막는다. 구조적 보장과 정리 가능성을 함께 지켜 세 방식 중 가장 좋다. 그러나 안내성 경고를 강제 실패로 바꾸는 것이므로 실제 작업 공간에서 경고를 운용해 오탐률을 확인한 뒤 강화해야 한다. 최악 추정은 본래 보수적이다. 후속 대안으로 남긴다.

**QUERY_MAX_BYTES 확대.** 가장 간단하며 오늘날 컨텍스트 창에서 4KB 주입은 과도하지 않다. 그러나 2048은 기술적 한계가 아니라 낮은 우선순위 선호가 차지할 주의력에 관한 판단이다. 늘리면 이번 장의 설정·문체 판단과 경쟁하게 되며 #368에서 이미 이 절충을 정했으므로 채택하지 않는다.

**주입 포장 압축(`kind` 제거, `scope` 평탄화).** 항목당 고정 비용이 100바이트이고 단언 상한은 120이므로 표현 손실 없이 2048바이트 용량을 약 11개에서 16개로 늘릴 수 있다. 그러나 주입 계약인 `compact_item`의 필드 집합을 바꾸므로 별도 기록·평가가 필요하여 이번에는 함께 하지 않는다.

## Consequences

- 작가는 예산 초과 전에 단순 `APxxx` 번호뿐 아니라 단언 첫 문장까지 포함한 개별 경고를 받는다.
- 초과 시 낮은 중요도부터 제외하므로 작가가 `importance`를 표시할 동기가 커진다. 문서에도 “모두 high로 설정하지 말라”고 명시한다. 이미 모든 항목을 `high`로 지정한 공간에는 효과가 없어 정리 때 낮춰야 한다.
- 단언이 약 50바이트라면 항목이 열몇 개일 때부터 매 쓰기에 `warnings`가 나타난다. 일회성 사건이 아니라 지속적으로 참인 상태를 설명하므로 의도된 동작이다.
- 추정은 전역＋차원별 가장 무거운 부분집합의 최악 조건이므로 자기 책에서는 실제 누락이 없는 작가에게도 경고할 수 있다. 거짓 양성은 추가 안내 한 번이지만 거짓 음성은 이번에 고치려는 버그이므로 보수적인 편을 택한다.
- 주입 예산과 별도로 `PROFILE_MAX_BYTES = 12288` 절대 상한이 있다. 로컬 실측에서는 active 84개 이후 쓰기가 바로 실패했고 주입 예산 영향보다 훨씬 뒤였다. 이번 경고 단계에는 포함하지 않고 문서에 존재와 처리법만 명시한다.
- `query --kind` 필수화는 호환성을 깨는 변경이며 `assertion` 상한 축소는 신규 항목에만 영향을 준다. 둘 다 출시 시 CHANGELOG의 `Changed`에 기록해야 한다.
