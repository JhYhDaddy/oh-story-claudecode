# 작가 기억 프로토콜

작가 기억은 장편·단편 집필 skill이 관리하며 작가가 명시적으로 표현한, 세션을 넘어 재사용할 창작 선호를 저장한다. 추가·확인·교체·삭제는 이 파일을 따른다. 정리·용량·충돌·마이그레이션·단일 작품 배치는 [author-memory-maintenance.md](author-memory-maintenance.md)를 참조한다. 소설의 사실은 계속 해당 작품의 설정과 추적 자료에 쓴다.

## 범위와 우선순위

불러오기 우선순위는 높은 것부터 다음과 같다.

1. 안전, 사용자 승인 범위, 명시적인 플랫폼 납품 요구, 글자 수·파일 계약. 문장 길이·시점·수사·문장부호 선호는 덮어쓸 수 없는 하드 게이트가 아니다.
2. 사용자가 현재 요청에서 명시한 요구.
3. 현재 작품의 `설정/문체.md`, 장르 방향, 상세 개요, 기타 프로젝트 설정.
4. 작가 기억의 현재 작품 선호.
5. 작가 기억의 장르·절차·전역 선호.
6. 벤치마크 자료, 일반 방법, 기본값.

표현 차원별로 적용 범위가 가장 좁은 요구를 고른다. 낮은 우선순위는 빠진 항목만 보충하며 높은 우선순위와 병렬로 적용하지 않는다. 일반 references가 필수·금지를 선언해도 이 순서는 바뀌지 않는다. 검토에서는 작가가 의도한 표현 선택 자체로 감점하지 않지만 실제 가독성·인과 문제는 정상 평가한다.

작가 기억을 이유로 작품의 사실을 `.story/작가기억/`에 쓰거나 검토 rubric을 낮추거나 AI 말투 제거 과정에서 플롯 의도를 바꾸면 안 된다. 소설의 사실은 각 작품의 `추적/`와 `설정/`에서 관리한다.

## 저장과 경로 선택

기억은 2계층이다. `{工作区}/.story/작가기억/`에는 global / genre / workflow 항목을 `AP` 번호로 저장한다. `{书}/.story/작가기억/`에는 해당 작품의 book 항목만 `BP` 번호로 저장한다. 각 계층의 `작가프로필.md`는 유효 항목을, `확인대기.md`는 제약에 참여하지 않는 후보를 표시한다. 모두 state에서 생성하므로 직접 수정하지 않는다. 기억이 없어도 정상 창작하며 첫 `record`가 자동 생성한다.

- `--workspace`는 명시적으로 전달해야 한다. 여러 작품·`.active-book`·`장편/`·`단편/`·`작품분석실/`를 담는 창작 작업공간 루트다. 기존 기억이 있으면 `book` 필드가 없는 프로젝트 state가 위치한 가장 가까운 조상 디렉터리다. `장편/`·`단편/` 아래의 작품 디렉터리는 절대 `--workspace`로 삼지 않고 사용자 홈도 기본 작업공간으로 삼지 않는다.
- `--book-root`는 현재 작품의 프로젝트 디렉터리다. 장편에는 `설정/`·`본문/`, 단편에는 `설정.md`·`본문.md`가 있으며 `.active-book`으로 지정할 수도 있다. 작품명은 작품 state에 기록한 이름을 기본으로 하고 처음에는 디렉터리명을 쓰며 `--book`으로 덮어쓸 수 있다. 작품 루트와 작업공간이 같으면 유지·관리 문서의 단일 작품 배치를 읽는다.
- ID 접두사가 store를 정한다. `decide` / `forget`은 `item_id`를 따른다(`AP`는 프로젝트, `BP`는 작품). `remember` / `replace`는 `scope.level`을 따른다(`book`은 작품, 나머지는 프로젝트). 작품 작업에는 `--book-root`가 필수이며 누락하면 오류를 내고 프로젝트에 대신 쓰지 않는다.
- `replace`와 `conflicts_with`는 store를 넘을 수 없다. 작품 예외는 우선순위로 전역 규칙을 덮어쓰므로 충돌이 아니며 바로 book 항목으로 `remember`한다. 전역 규칙을 작품 규칙으로 바꾸려면 `forget` + `remember` 두 이벤트로 나눈다.

## 조회

집필 진입점은 `query` 명령을 제공한다. 장편 본문은 조립 스크립트가 대신 조회한다. 명령이 없는 장편 설정·개요 작업은 `story_design` + `workflow` + `interaction`을 조회하고 결과는 주 세션에만 주며 본문 에이전트에는 넘기지 않는다. 집필 흐름에서 조회한 관련 선호와 문체 판정을 AI 말투 제거·검토에 전달한다. 후속 작업은 자체 조회·기록하지 않는다. 매핑 표는 유지·관리 문서를 참조한다. state가 있을 때만 조회하며 양쪽에 없으면 빈 결과를 반환하고 쓰기는 0회다. 결과는 프로젝트와 `--book-root`가 가리키는 작품 기억을 합친다. 이 인수가 없으면 작품 항목을 얻지 못한다. `--kind`는 필수다. 실행자에게는 항목별 원래 표현+번호 한 줄인 `lines`만 주며 조회 한 번은 ≤2048바이트다.

보통의 창작은 로컬 `query`를 한 번만 하고 반환된 `lines`만 실행자에게 전달한다. 전체 프로필·근거·후보·변경 기록은 컨텍스트에 넣지 않는다. 조회 항목은 낮은 우선순위의 성향으로 자연스럽게 반영하며 모두 맞추려고 연결성·리듬·글자 수·작품 문체를 희생하지 않는다. **`omitted_ids`가 비어 있지 않으면 이번 컨텍스트에 넣지 못한 선호가 있다는 뜻이다.** `omitted_summaries`대로 작가에게 알리고 작가 기억 정리를 권한다. 전체 프로필을 읽어 예산을 우회하지 않는다. 확인 대기 항목은 창작 제약에 참여하지 않으며 작가가 직접 열람하거나 후보를 모아 검토하거나 새 선호가 active 항목과 충돌할 때 제시한다.

## 무엇을 어떻게 기억할 것인가

모든 사용자 메시지를 기록하는 prompt hook을 설치하지 않고 작가가 말하지 않을 때 관찰하지 않는다. 명시적으로 표현한 선호만 기억한다. 장기 습관 여부는 에이전트가 판단하며 확신이 없으면 실행만 하고 기록하지 않는다. 작가는 ‘기억해 줘: …’라고 명시할 수 있고 영수증으로 확인한다.

| 입력 근거 | 처리 |
|---|---|
| ‘앞으로 항상 이렇게’, ‘나는 늘 …하는 편’처럼 직접적·안정적이며 범위가 명확한 원문 | `active`, `source=explicit_user` |
| 사용자가 도우미의 장기적 제안을 명시적으로 수락 | `active`, `source=accepted_suggestion` |
| 작가의 말이 장기 선호 같지만 범위·안정성이 모호함 | `pending`, 현재 합리적으로 가장 좁은 범위. 확인 대기는 작가 자신의 말에서만 생성 |
| 비슷한 수정의 반복, 완성 원고·작업 이력에서 관찰한 패턴 | 기록·추론하지 않음. 작가가 말하지 않은 선호는 기억하지 않음 |
| ‘이번 장에는 …하지 마’, ‘이번에는 …해 줘’ 같은 일회성 요구 | 실행만 하고 기록하지 않음 |
| 인물·시간선·복선·세계관·현재 플롯 방향 | 프로젝트 설정/추적에 쓰고 작가 기억에는 쓰지 않음 |
| 도우미가 만든 텍스트·기본 템플릿·도구 경고·rubric 결론 | 자기 학습하지 않음 |

부정어·한정어·적용 범위를 보존한다. `quote`에는 원문을 쓰고 `assertion`은 의미를 바꾸지 않는 간결한 요약만 한다. **새 항목은 한 문장, ≤120바이트(원문의 중국어 기준 약 40자)**다. 넘으면 표현을 압축하고 한정 조건을 자르지 않는다. 배경은 prompt에 들어가지 않는 `reason`에 쓰며 새 필드를 만들지 않는다.

**선호 하나는 기록 하나이며 예외·한정 조건을 별도 항목으로 떼면 안 된다.** ‘앞으로 대시는 적게 쓰고 대화에서도 쓰지 마. 단, 말이 끊길 때는 괜찮아’는 ‘대시는 적게 쓰고 대화에서도 쓰지 않되 말이 끊길 때만 남긴다’로 함께 기록한다. 예산 초과 시 항목별로 빠지므로 분리하면 예외만 사라져 작가의 조건부 요구가 절대 금지로 바뀔 수 있다. 원문에 **서로 독립적인 여러 선호**, 예컨대 짧은 문장을 많이 쓰기 + 장 끝에 후킹 남기기가 있을 때만 나눈다.

범위: 이 작품/이 인물/이번 연재 → `book`, 도시물/이런 장르 → `genre`, 납품·검사·확인 속도 같은 작업 습관 → `workflow`, 앞으로/항상/내 습관이며 더 좁은 한정이 없으면 → `global`. 모호하지만 안정적일 수 있으면 가장 좁은 합리적 범위로 `pending` 처리한다.

유형은 `prose_style`, `story_design`, `workflow`, `delivery`, `interaction`이다. 확신도와 중요도는 모두 `low | medium | high`다. 초과 시 중요도가 낮은 것을 먼저 빼므로 실제 비중에 맞게 적고 전부 `high`로 하지 않는다. `source`는 `explicit_user`, `accepted_suggestion`, `manual`만 받으며 도구는 추론 출처를 거부한다.

## 확인·교체·삭제·충돌

- 같은 유형·범위·요약 텍스트가 다시 나오면 스크립트는 기존 항목에 근거와 확인 횟수를 더해 강화하며 중복 생성하지 않는다.
- 새 선호가 같은 store의 active 항목과 모순되면 `conflict` 후보로 기록하고 `conflicts_with`에 충돌 ID를 적는다. 이번 작업은 현재 요청을 따른다. 작품 예외와 전역 규칙은 충돌이 아니다. 충돌 후보는 바로 activate할 수 없으며 확정 절차는 유지·관리 문서의 충돌 후보를 따른다.
- pending에는 `decide=activate|reject`를 쓴다. 같은 범위의 규칙을 개정하면 `replace`로 새 항목을 활성화하고 옛 항목을 `superseded`로 표시한다. 작가가 기존 규칙을 명시적으로 철회하거나 범위를 바꿀 때만 범위를 넘어 교체한다.
- 작가가 잊어 달라거나 더는 자신의 습관이 아니라고 하면 `forget`을 사용한다. 근거 이력은 남지만 다시 불러오지 않는다. active 항목의 의미를 몰래 제자리 수정하지 않는다. 의미 변경에는 반드시 replace를 써야 이력을 감사할 수 있다.

## 작가에게 영수증 전달하기

답변은 코드 블록·인용 형식 없이 평문 두 줄로 한다. 첫 줄에는 무엇을 기억했고 어느 작품·상황에 적용하는지 자연스럽게 한 문장으로 말한다. 예: ‘기억했어요. 《{작품명}》의 대화에는 항상 「」를 쓰고, 앞으로 이 작품에서는 그대로 따를게요. 바꾸고 싶으면 말씀해 주세요.’ 둘째 줄에는 증빙용 기계 영수증을 쓴다. 예: ‘기술 메모: Author Memory Receipt: r1 · BP001’.

- 확인·교체·삭제도 같은 방식이다. ‘이 항목이 적용됐어요: …’, ‘…로 바꿨고 이전의 …는 더는 쓰지 않아요’, ‘…를 잊었어요’. 확인 대기만 등록했다면 ‘우선 확인 대기에 넣었고 확인이라고 하시면 적용돼요’라고 말한다. 충돌은 어느 기존 습관과 충돌하는지 원래 표현으로 설명한다.
- `warnings` / `omitted_ids`를 그대로 붙이지 않는다. ‘기억한 습관이 많아 본문 집필에 이 항목들은 포함되지 않아요: …’라고 말하고 작가 기억 정리를 권한다. `warnings`는 최악의 추정이므로 ‘포함되지 않을 수 있어요’로 말한다. 바이트·prompt·kind·scope는 언급하지 않고 번호는 원래 표현에 붙여서만 표시한다.

## 도구 실행

`python3`, `python`, `py -3` 순서로 Python 3을 찾고 현재 집필 skill 루트의 로컬 복사본을 실행한다.

```text
{PYTHON} {当前 skill 根}/scripts/author_memory_commit.py record --workspace {工作区} [--book-root {书目录}] --input {工作区}/.story/work/作者记忆-事件.json
{PYTHON} {当前 skill 根}/scripts/author_memory_commit.py query  --workspace {工作区} --book-root {书目录} --kind {类型}(필수, 반복 가능) [--genre {题材}] [--workflow {流程}]
```

- 모든 하위 명령에 `--book {书名}`을 추가할 수 있다. 특정 작품을 쓸 때는 반드시 `--book-root`를 붙인다. 이벤트 JSON은 시스템 `/tmp`가 아닌 `{工作区}/.story/work/`에 쓰고 성공 후 삭제한다. book 항목의 `scope.value`는 작품 store에 기록한 이름이며 최초에는 디렉터리명을 쓴다.
- 명시적인 기억/확인/교체/삭제는 모두 단일 이벤트 `record`로 처리한다. 해당 store의 현재 수정 번호를 자동으로 읽고 최초 초기화도 자동 수행하므로 번호를 직접 읽거나 다중 작업 트랜잭션을 조립하지 않는다. 같은 `event_id`와 같은 내용은 멱등적으로 원래 영수증을 반환하며 내용이 다르면 실패한다. 반환된 `store` / `book`이 기록한 계층을 알려 준다.
- 성공해야 `Author Memory Receipt: rN · APxxx`가 나온다. 영수증 없이 기억했다고 말하면 안 된다. **주입 예산 때문에 쓰기가 실패하지 않는다.** `warnings`는 알림일 뿐이며 다른 계층 store를 읽지 못한 경우도 여기에 표시한다. 위 방식으로 전달한다. 영수증이 있으면 이미 기억한 것이므로 `event_id`를 바꿔 재시도하지 않는다.

## 이벤트 형식

추가 또는 강화(`record` 입력, book 범위에는 `--book-root` 전달):

```json
{
  "schema_version": 1,
  "event_id": "conversation-2026-08-25-message-42",
  "operation": {
    "action": "remember",
    "preference": {
      "kind": "prose_style",
      "scope": {"level": "global", "value": null},
      "assertion": "대사는 짧게, 감정은 행동으로 잇고 긴 설명은 피한다",
      "quote": "앞으로 대사는 짧게 하고 감정은 행동에 담아 주세요. 인물이 길게 설명하지 않게 해 주세요.",
      "source_ref": "conversation:2026-08-25",
      "source": "explicit_user",
      "confidence": "high",
      "importance": "high",
      "status": "active",
      "reason": "사용자가 앞으로라는 말로 장기 선호를 명시함",
      "conflicts_with": []
    }
  }
}
```

확인 대기는 `"status": "pending"`을 쓴다. 충돌 후보는 `conflict`와 같은 store의 active ID를 사용한다. 확인·교체·삭제 시 아래 객체를 새 이벤트의 `operation`에 넣고 `BP` 번호에는 `--book-root`를 전달한다. `replace.preference`의 필드는 위와 같지만 `status`, `conflicts_with`를 주지 않으며 새 항목은 바로 active가 된다.
